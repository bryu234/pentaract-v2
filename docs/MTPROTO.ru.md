# Подключение через указанный MTProto server

Pentaract обращается по HTTP к локальному контейнеру `telegram-bot-api`. Тот
соединяется с Telegram по MTProto через TDLib. Для передачи файлов доступ к
`api.telegram.org` не нужен. Адрес из **Production configuration** на
[my.telegram.org/apps](https://my.telegram.org/apps) можно задать как приоритетный
для соответствующего дата-центра (DC).

## Настройка

Оставьте `PENTARACT_TELEGRAM_API_URL=http://telegram-bot-api:8081`. В `.env` задайте:

```dotenv
PENTARACT_MTPROTO_DC_ID=2
PENTARACT_MTPROTO_SERVER=<PRODUCTION_IP>
PENTARACT_MTPROTO_PORT=<PRODUCTION_PORT>
```

Подставьте номер DC, IP и порт именно из **Production configuration**. Поддерживаются
IPv4 и IPv6 без квадратных скобок. Нужно заполнить все три поля либо оставить все
пустыми для штатного выбора адресов TDLib. `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`
по-прежнему обязательны. Изменение адреса требует пересоздания Telegram-контейнера;
пересборка нужна при изменении кода. Команда ниже выполняет оба шага с кешем Docker.

```bash
make telegram-build
make telegram-check
make telegram-restart
make telegram-logs
```

`telegram-check` проверяет параметры без соединения с Telegram. `telegram-restart`
пересоздаёт только Telegram-контейнер, сохраняя volumes. Его healthcheck проверяет
локальный HTTP-порт, а не доступность Telegram.

Указанный адрес получает приоритет в своём DC. При ошибках TDLib выбирает другие
доступные адреса. Маршрутизация медиа и перенаправления между DC остаются штатными.
Новая сессия начинает работу с заданного DC, существующая сохраняет свой основной
DC. Telegram может потребовать соединения с другими дата-центрами: успешного `nc`
до одного IP недостаточно для проверки авторизации и файлов.
[Документация Telegram о DC](https://core.telegram.org/api/datacenter).

Публичные RSA-ключи Telegram уже встроены в TDLib. Вводить их, MTProxy secret или
входить в пользовательский аккаунт для этой настройки не нужно.
**Test configuration относится к отдельной среде Telegram**: действующий обычный
бот и канал в ней не работают. Эта настройка предназначена только для Production.
[Описание тестовой среды](https://core.telegram.org/bots/features#creating-a-bot-in-the-test-environment).

## Проверка на сервере с действующим ботом и каналом

1. Подготовьте на сервере отдельную копию ветки `improvements` с пустыми volumes
   PostgreSQL/Telegram и новым каталогом `data/`. Для этой проверки не копируйте и
   не восстанавливайте базу, ключ и Telegram-сессию с ноутбука. Если такой Compose
   проект на сервере уже существует, используйте отдельный каталог и уникальное
   `COMPOSE_PROJECT_NAME` во **всех** командах. Не удаляйте существующие volumes.
2. Выполните `make init`, заполните `.env`: API ID/hash, Production DC/IP/порт,
   свободный `PENTARACT_HTTP_PORT` и соответствующий `PENTARACT_PUBLIC_URL`.
   Выполните `make telegram-build` и `make telegram-check`.
3. Перед подключением того же бота остановите на ноутбуке приложение и локальный
   Bot API: `docker compose stop app telegram-bot-api`. Сохраните его базу, ключ и
   volumes. Не запускайте два Pentaract с одним ботом одновременно во время проверки.
4. На сервере выполните `make up`: команда проверит порт. Зарегистрируйте локальную
   учётную запись Pentaract и задайте действующий bot token и ID канала.
   **Cloud logOut оставьте выключенным**, поскольку бот уже работает через локальный
   Bot API. Если бот ещё зарегистрирован в облачном Bot API, предварительный logOut
   нужно выполнить из сети с доступом к `api.telegram.org`; адрес DC его не заменяет.
5. Загрузите новый пробный файл, дождитесь окончания обработки, скачайте его и
   сравните SHA-256: `sha256sum` в Linux или `shasum -a 256` в macOS. Проверьте также
   файл больше размера чанка. Перезапустите Telegram-сервис и повторите скачивание.
   Повторное скачивание может использовать локальный кеш; успешная новая загрузка
   дополнительно подтверждает связь с Telegram.
6. Посмотрите `make telegram-logs`: `route=preferred` — попытка подключения к
   указанному адресу, `fallback` — к другому адресу этого DC, `other-dc` — к другому
   DC. Это сообщения о **попытках соединения**, а не о завершённой авторизации.
   Сопоставляйте их с результатами передачи файлов. Если был fallback, успешная
   передача сама по себе не доказывает работоспособность заданного IP.
7. После проверки остановите app и Telegram на сервере. Только затем возобновите
   ноутбук через `make up`. Сохраните тестовую базу и ключ, пока нужны загруженные
   через неё файлы. Эти новые файлы не появятся в каталоге ноутбука автоматически;
   прежние файлы канала не импортируются и не удаляются.

Перенос действующего хранилища — следующий отдельный этап, для которого нужны
исходная база и ключ шифрования. Локальные обычные копии файлов не заменяют каталог
хранилища в PostgreSQL.

## Проверки и сопровождение

Патч применяется к TDLib `bc9c263e2bfee06aaab41e82db51a103376030bc` внутри
закреплённой версии Bot API. Несовпадение версии или ошибка применения останавливают
сборку. Адрес добавляется после штатных и сохранённых/полученных от Telegram адресов;
переопределение не записывается в сохранённый список DC. Чтобы отключить настройку,
очистите все три переменные и выполните `make telegram-restart`. Основной DC
существующей сессии при этом сохраняется.

При сборке выполняются проверки параметров, начального DC и тесты настоящего
`DcOptionsSet` TDLib: приоритет, отказ адреса, обновление конфигурации и другие DC.
Готовый образ дополнительно проверяет запуск бинарников и наличие библиотек.
Диагностика не включает подробные upstream-логи, которые могут содержать токены.
Параметр `--proxy` стандартного Bot API относится к webhook-запросам и для этой
задачи не используется.
